1.1  What Genuin Does
Genuin is a short-form video platform that powers community-led video experiences on publisher destinations. Publishers integrate the Genuin SDK — a lightweight JavaScript snippet — to render a personalised vertical video feed within their existing page or app surface. Genuin's recommendation engine handles all content assembly and delivery; the publisher provides the destination.
Advertising runs across this inventory in two modes. Direct-sold placements (Sponsored Takeover, Sponsored Post) are controlled by Genuin's ad engine server-side. Programmatic placements (in-feed and in-stream video) are served via connected SSPs/DSPs through standard oRTB/VAST/VMAP pipelines, with Genuin providing the inventory across the network and the ad slot.
1.2  Genuin's Approach to Identity & Targeting
A core principle of Genuin's ad stack is that Genuin does not perform audience targeting itself. Genuin's role is to surface identity signals in every ad opportunity and bid request — enabling buying partners to apply their own targeting logic. This applies across both ad delivery modes:
This philosophy keeps Genuin's stack lean, avoids the commercial and privacy complexity of managing audience segment resolution internally, and ensures that buying partners retain full control over their targeting methodology.
1.3  Why LiveRamp & Why This Document
Across all active client proposals — retail media networks, commerce media networks, brand partners — LiveRamp has been specified as the preferred identity resolution infrastructure. These clients require identity matching to push audience segments into their buying systems and to receive Genuin exposure data back for closed-loop attribution.
Genuin does not yet have a formal LiveRamp integration. This document captures Genuin's current working understanding of how that integration would operate, informed by LiveRamp's published documentation, and sets out the specific questions Genuin needs validated before any client onboarding begins.
Genuin's preferred integration path is to participate in the client's existing LiveRamp data clean room as a publisher, rather than acquiring a separate LiveRamp seat of its own. In this model, Genuin contributes its user identifiers to the client's clean room environment; the client's infrastructure handles all identity resolution, segment matching, and audience definition. This section describes how Genuin understands that flow to work, and the key questions that need to be resolved.
2.1  Three Design Principles for the Integration
Genuin resolves its own users independently — Genuin does not participate in a brand's data clean room to generate identity signals. Genuin's identity resolution runs entirely on its own infrastructure — either as a batch mapping process or via a real-time client-side tag embedded in the Genuin player. The resulting RampID or identity envelope is Genuin's own first-party signal, generated without any dependency on the brand's environment.
Identity in the request path — The integration must produce an identity signal — decipherable by the buying partner — that travels in the ad or bid request itself. This enables real-time targeting decisions without a separate audience-push workflow. An identity envelope in the request is the target state for both programmatic and direct paths.
One implementation for both paths — Genuin strongly prefers a single identity mechanism that works for both programmatic and direct deal delivery. Separate implementations for each path would significantly increase integration complexity and maintenance overhead.

3.1  The Envelope as a Unified Signal
Genuin's target architecture uses a single identity signal format — the LiveRamp identity envelope — in both the programmatic bid request and the direct ad API request. This means the envelope generation mechanism is the same regardless of delivery path; what differs is how the envelope is decrypted and acted upon at the buying side.
3.2  Generation Path A — Local Encoder (Batch, Offline)
Local Encoder is the primary generation mechanism for Genuin. It runs as a Docker image within Genuin's own cloud environment, processes batch files of known user identifiers, and outputs identity envelopes without Genuin's consumer data ever leaving its infrastructure.
Supported inputs (per LiveRamp docs) — Plaintext email, SHA-256 hashed email, phone number, mobile device IDs (IDFA and AAID). Note: LiveRamp's documentation states that mobile device IDs are supported for Activation use cases only, not for Addressability (envelope) output. This is a key open question for Genuin's device-ID user segment — see Section 4.
Applies to — Both programmatic and direct paths. Local Encoder is the preferred generation mechanism precisely because it is path-agnostic: it produces an envelope that can be passed in either context.
3.3  Generation Path B — ATS (Authenticated Traffic Solution, Real-Time)
ATS generates a fresh identity envelope in real-time at the moment a user provides their email address in-session — through a sign-in, newsletter sign-up, or registration wall. The envelope is returned to the publisher's first-party storage and can be passed into the bid stream.
Applies to programmatic — Yes, straightforwardly. The ATS-generated envelope travels through Prebid.js or equivalent header bidding setup into the bid stream, where the SSP's Sidecar decrypts it. This is ATS's primary documented use case.
Applies to direct — Via ATS Direct, which is LiveRamp's documented mechanism for direct media buys without an SSP. In ATS Direct, the brand activates its segments to the publisher's Console account in LiveRamp Connect. When a matched user is identified via ATS envelope, the Deal ID for that user is returned to the publisher's browser and used by Google Publisher Tag (GPT) to communicate with Google Ad Manager (GAM). This means ATS Direct is tightly coupled to GAM as the ad server — it is not a generic ad API call model.
Constraint for Genuin — ATS is designed for publisher-owned pages where users authenticate directly. The Genuin SDK is an embedded third-party snippet within a publisher page — Genuin does not own the authentication event. Additionally, ATS Direct's dependency on GAM does not match Genuin's direct ad serving architecture. ATS is therefore a secondary path for authenticated sessions where the publisher surfaces an email signal to the SDK, not Genuin's primary generation mechanism.
3.4  Decryption in the Direct Path — The Open Question
In the programmatic path, decryption is handled by the SSP running Sidecar — a well-documented, standard infrastructure component. In the direct path, there is no SSP. Genuin's preferred model is that the buying partner handles decryption on their own server, using LiveRamp's Envelope Decryption API, which is a documented endpoint in LiveRamp's developer documentation.

4.2  Signal Category 1 — Hashed Email (Signed-In Users)
For users who have authenticated on a publisher page, Genuin holds an email address that can be SHA-256 hashed before submission to LiveRamp. This is the highest-fidelity signal available and the anchor of Genuin's identity approach.
4.3  Signal Category 2 — Mobile Device IDs (Tracking-Enabled Users)
For mobile users who have not opted out of device tracking, Genuin's SDK can capture the platform advertising identifier: IDFA on iOS where ATT consent has been granted, or GAID on Android. These are deterministic signals where available, but coverage has declined significantly due to Apple's ATT framework.
4.4  Signal Category 3 — Fingerprint Signals (Unauthenticated Users)
For users who are not signed in and whose device ID is inaccessible, Genuin can observe a combination of browser and device signals via the SDK: IP address, user agent string, device model and make, and coarse location. These signals could support probabilistic (fingerprint-based) matching, but this approach does not appear in any LiveRamp documentation Genuin has reviewed.
4.5  Combined Signal Strategy
In practice, Genuin would submit all available signals simultaneously — HEM for registered users, device IDs for tracking-enabled users (subject to Addressability support being confirmed), and fingerprint signals if supported — to maximise total addressable reach. The overall match rate achievable depends directly on these open questions being resolved.

1.  Overview of Genuin & the Need for Formalisation
Programmatic | DSP owns targeting end-to-end
Genuin passes an identity envelope in the bid request. The SSP's Sidecar application decrypts the envelope and surfaces the resolved RampID to the DSP. The DSP applies its own segment matching and targeting logic. Genuin has no visibility into segment definitions and takes no targeting action.
Direct (BYOA) | Buying partner owns targeting via API 
Genuin sends an ad request to the buying partner via API, including the identity envelope as a signal. The buying partner's ad decision engine resolves the identity using their own LiveRamp access and applies their own targeting, creative selection, and optimisation. Genuin serves what the partner decides. This is the BYOA (Bring Your Own Algorithm) model for direct deals onsite and sponsored post and takeovers offsite across the network.

2.  Expected Integration Flow into a Client's Data Clean Room Account
Validation request — Does LiveRamp support a Genuin participating in a brand's data clean room without Genuin holding their own commercial LiveRamp seat? If yes, what is the nature of the account required, what are steps for a clean room customer to add Genuin, and what is the onboarding path?
1 | Genuin resolves its user pool to RampIDs
Genuin resolves its own users to RampIDs independently, using one or both of two mechanisms. The batch path uses Local Encoder: a Docker-based tool that processes Genuin's known user signals (SHA-256 hashed email, device IDs where supported) within Genuin's own cloud environment and outputs a genuinID → identity envelope mapping. This mapping is stored as a lookup table and refreshed as envelopes approach expiry. The real-time path uses a LiveRamp ATS JavaScript tag embedded in Genuin's player: when a known user is active in session (for example, because the publisher has surfaced an email signal), ATS generates an envelope client-side and stores it in first-party storage. The two paths are complementary — batch covers the registered user base; the JS tag extends coverage to in-session authenticated users.
2 | Genuin includes the envelope in every ad and bid request
For any user with a resolved envelope — whether generated via the batch mapping or the real-time JS tag — Genuin includes that envelope in the outbound request. For programmatic inventory this is the bid request; for direct inventory (BYOA) this is the ad API request to the buying partner's server. The envelope is the single identity signal passed in the request path, consistent across both delivery modes
3 | Buying partner resolves the envelope and applies targeting
For programmatic inventory, the SSP's Sidecar application decrypts the envelope and surfaces the RampID to the DSP, which applies its own segment logic. For direct inventory (BYOA), the buying partner's server receives the envelope in the ad API request and calls LiveRamp's Envelope Decryption API on their side to resolve the RampID and apply their targeting. In both cases, Genuin takes no targeting action.
4 | Exposure and engagement data returns to the client's clean room
Post-delivery, Genuin exports user-level exposure and engagement logs — tokenised at the genuinID level — back to the client. The client uses their LiveRamp environment to re-link these to RampIDs for attribution against their own downstream conversion events within the clean room.
Key open question — For Step 5, the direct path assumes the buying partner calls LiveRamp's Envelope Decryption API on their own infrastructure using their own LiveRamp access. This keeps Genuin out of the decryption chain entirely. We need to confirm with LiveRamp whether this is a supported pattern — i.e., whether a brand/buyer can call the decryption API to resolve an envelope generated by a publisher — and what contractual or technical prerequisites apply.
