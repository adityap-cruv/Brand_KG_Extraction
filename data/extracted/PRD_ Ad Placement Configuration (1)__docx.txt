🌟 Product-Level Questions
What generative and regenerative features are we adding as part of this user story?
We will introduce a new concept of optimised monetisation using AI wherein we’re able to best optimise the engagement + monetisation of our partners with target criterias. The users will also be able to chat with the LLM to understand what settings have been made and how they’re impacting their current engagement and monetisation. The LLM is connected to an MCP which in turn provides capabilities around changing the configurations that we have within ad config settings. The MCP will also have access to engagement and monetisation analytics and is able to explain changes in settings and the impact of such changes via a conversational interface. In v1 of this implementation, we will look at activating ads and in v2, we will add the generative features.
How the company, the destination and subscribers are generating revenue with this user story ?
We create the ability to generate revenue by showing programmatic ads within brand content videos. Brands will have the ability to activate different kinds of ads such as in-stream, in-feed and overlay ads and control the frequency of ads that their users see. We will also provide different default configurations where brands can choose to either maximise their earnings Or optimise between engagement and monetisation Or choose to completely customise the configurations as per their requirements. In v1, we will focus on in-stream ads config and in v2, we will add in-feed and display/native ads as well.
How consumers are getting an improved experience with this users story ?
Unlike traditional banners which can be big detractors to user experience, we’re looking to redefine how engagement and ads work at a level which not just reduces bad user experience(of ads) but in fact is a net net addition to user experience. We achieve this by creating LLM ads wherein a user receives ads within their LLM conversation itself which is activated when a user clicks on the Octo button. We will introduce LLM ads in v3 implementation of ad config.

BCC “Save” Click
When the brand admin user clicks on the “Save” button, the settings defined in the ad configuration are persisted in the database against the brand.
SDK Initialization
During SDK(web/iOS/Android) Initialization, SDK will fetch ad_config.json and store it in AdPreferences. In case an existing ad_config.json exists from the previous session, the new values will rewrite the existing values.
Enable In-stream ads at brand level
BCC Requirements:
Required Field: “In-stream video ads”
UX Type: Toggle
Field Type: Boolean
Corresponding field in ad_config: “in_stream_video_ads”
SDK Requirements:
If “in_stream_video_ads” == true in ad_config.json, initialize IMA SDK to generate in-stream ad requests
If “in_stream_video_ads” == false in ad_config.json, do not generate any in-stream ad requests
IMPORTANT NOTE: in-stream ad requests should be made for the next video in queue such that we’re ready with the ad response before the video plays to avoid any revenue losses due to latency. Ensure that adsRenderingSettings.enablePreloading = true; in the IMA SDK so that the in-stream ad response can start downloading media for the ad while the current video is playing. First video in the feed is always ads free. While the first video is playing, we request for ads for the next ad enabled video(basis frequency settings) and continue.

Enable ads in the next video basis frequency
BCC Requirements:
Required Field: “Frequency”, “Swipes” AND “Seconds of Watch Time”
UX Type: Selection
Field Type(s): int
Corresponding field in ad_config: "in_stream_video_ads_swipe_frequency" AND in_stream_video_ads_seconds_frequency
SDK Requirements:
Create 2 new variables:
“ads_free_content_watch_time”: This variable is initialized as “0” at the start of the video feed. The variable will measure the content watch time in seconds. After every ad completion[Ad completion can be the complete ad watched by the user OR user pressing on the skip button of the ad OR user scrolling to the next video - Essentially, as soon as the user is done watching the ad video and moves to the first frame of the next content view(of the same video Or the next video)], this variable is reset to “0”. This ensures that this variable measures the ads free continuous content watch time for any specific user.
“ads_free_content_swipes”: This variable is initialized as “0” at the start of the video feed. The variable will measure the content swipes(either automatic movement to next video Or user initiated). After every ad completion[same logic as above], this variable is reset to “0”. This ensures that this variable measures the number of content videos seen(either complete or incomplete) seen by the user without any ads.
Whenever we’re requesting ads for a next video in queue, we will validate the following logic:
If (ads_free_content_watch_time < in_stream_video_ads_seconds_frequency AND ads_free_content_swipes < in_stream_video_ads_swipe_frequency), then do not generate the next in-stream ad request in queue.
If (ads_free_content_watch_time >= in_stream_video_ads_seconds_frequency OR ads_free_content_swipes >= in_stream_video_ads_swipe_frequency), then generate the in-stream next ad request in queue.

Define the behavior of in-stream ads for up and down scrolls
SDK Requirements:
In the current scope of this PRD, we will only consider a forward swipe as an eligible swipe for our frequency capping requirement. This means that we increment our “ads_free_content_swipes” variable only when the user(or system) swipes to the next content video. The variable does not get incremented if the user swipes to the previous content video. This ensures that we’re only requesting ads for the next sequenced videos in the feed. NOTE: This does not change the current implementation of how we handle one previous video where we keep the ad cached if the user back swipes once.
Define the behavior of in-stream ads frequency management in multi-video setups such as Carousel, grid layout etc
Backend Configuration Requirements(Not available on BCC):
Required Field: “Min Hover Time for Video Play Count”
UX Type: Number
Field Type: number, Default Value: 5
Corresponding field in ad_config: "in_stream_video_ads_min_hover_time"
SDK Requirements:
Defining the current scope of video plays in multi-video setups
Only one video plays at a time
Post video completion, videos can be looped OR a different video frame could start playing their video
A user may hover over a different video frame and the previously playing video will stop and the current hovered video will start playing
To ensure that we’re managing our frequency requirements correctly in multi-video setups, we will count a video looping OR moving to a different video frame as one swipe. This means that we will increment our “ads_free_content_swipes variable” when the current video starts looping post completion OR another video frame starts playing a video post previous video completion. Additionally, we will use the “in_stream_video_ads_min_hover_time” variable to identify the min video watch time we will consider as a new content video start. For example, if “in_stream_video_ads_min_hover_time” is set as 5 and the user hovers over a video for 3s and then hovers over a different video, then the first video where the user hovered for 3s will not lead to an increment in “ads_free_content_swipes” variable. However, if the user hovers over a video for 5s, we will increment the ads_free_content_swipes variable and count it as an in-stream ads free content video.
Handling Platform Nuances - To be updated in design(Shrushti Shah, Shubhangi singh)
Brands have a use case wherein they may want to enable ads only on a specific platform Or they may want to apply different ad settings for different platforms(web, android & iOS)
To manage this nuance, we will provide brands the ability to select these ad settings individually for each of the 3 platforms Or apply the same settings to all platforms. As such, we can have 4 different settings available for us. Please see the nuances of each setting below
Android specific: In this scenario, the key-value pair for “android” in the JSON is populated with the settings selected by the brand for android
iOS specific: In this scenario, the key-value pair for “ios” in the JSON is populated with the settings selected by the brand for android
Web specific: In this scenario, the key-value pair for “web” in the JSON is populated with the settings selected by the brand for android
Global: In this scenario, the key-value pairs for “web”, “ios” and “android” are populated with the settings selected by the brand
While passing the settings to a specific platform client SDK, we need only pass through the settings for that specific platform. For example, when the iOS SDK requests for ad configuration settings, we do not pass through settings for android and web, we selectively pass through the settings only for “ios” from the ad_config.json
Muting/Unmuting behaviour
IMA SDK doesn’t provide any standard solution to mute/unmute specific ads via its video play interface. This means that the user doesn’t have an option to mute/unmute ads from the video play; however, the user can reduce volume/mute using the hardware volume controls available with them.
IMA SDK does provide an ability to set the volume of the ads using the adsManager.setVolume() function. We will use this function for the default behaviour of sound for in-stream ads which supports our functionality requirement for allowing brands to choose a default preference for starting ads in a muted/unmuted state.
