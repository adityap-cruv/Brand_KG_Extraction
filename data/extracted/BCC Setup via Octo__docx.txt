About this document
This guide abstracts the core methodology for building AI agents that collect structured information through conversational interfaces. It covers the four foundational mechanisms for preventing drift and enforcing step-by-step form progression, and provides reusable templates you can adapt to any form-filling use case.
The patterns here apply equally to simple 3-question flows and complex multi-branch enterprise forms.

2. The Four Mechanisms
2.1  State Injection (Every Turn)
This is the single most impactful mechanism. The current step, total steps, and all previously collected answers must be injected into the system prompt on every turn — not just at the start.
2.2  Validation Layer (Application-side)
Never trust the model alone to determine whether an answer is valid. Build a typed validation layer in your application code that sits between the user's input and the next state transition.
The step counter only increments when validate() returns { valid: true }. Invalid responses trigger an immediate re-ask without advancing state.

Key Insight
The model has no persistent memory between turns. Every response is generated fresh from the conversation history. Any drift or state loss happens because the application layer didn't inject the current state explicitly.
// Pseudo-code: system prompt template
SYSTEM_PROMPT = `
  You are a form-filling agent. Your ONLY job is to collect
  answers to the form questions below, one at a time.

  CURRENT STATE:
  - Current step: {currentStep} of {totalSteps}
  - Answers collected so far: {collectedAnswers}
  - Steps remaining: {pendingSteps}

  RULES:
  - Ask ONLY the question for step {currentStep}
  - Do NOT advance until the user gives a valid answer
  - If the user goes off-topic, redirect in one sentence
`
Why this works
The model cannot lose track of state because you are re-declaring it on every API call. The conversation history provides context; the injected state provides ground truth.

Pro tip
Two or three concrete few-shot examples in the prompt outperform a long list of rules. Models follow demonstrated patterns more reliably than abstract instructions.
const TANGENT_PATTERNS = [
  /weather|news|sports|joke|story|recipe/i,
  /what is|tell me about|explain|help me with/i,
  /who are you|what can you do/i,
  /thanks|bye|hello|good morning/i
];

function isTangent(input) {
  return TANGENT_PATTERNS.some(p => p.test(input));
}

// In your message handler:
if (isTangent(userInput)) {

Field | Purpose
currentStep | The single source of truth for where the agent is. Injected into every system prompt.
totalSteps | May differ from your static step count if conditional branching is active.
answers | Map of step ID to collected value. Injected so the model can reference prior answers.
redirectCount | Useful for analytics and for triggering escalation after N redirects.
conditionalSkips | Steps to skip based on prior answers (e.g. skip Step 3 if Step 1 was 'No').
done | Terminal flag. Once true, all input is ignored.
function getNextStep(currentStep, answers) {
  if (currentStep === 1 && answers[1] === false) {
    return 'DONE'; // Skip all remaining steps
  }
  if (currentStep === 2 && !answers[2].includes('Octo')) {
    return 4; // Skip step 3 (Octo-only)
  }
  return currentStep + 1;
}
Design principle
Conditional logic belongs in your code, not in the model's reasoning. If you rely on the model to decide which step to skip, you introduce a new category of drift: logic drift.

Mechanism | Reliability | Implementation Cost
State injection every turn | Very High | Low — add to system prompt builder
Typed validation layer | Very High | Low — one function per step
Anti-drift prompt instructions | Medium-High | Low — copy template from Section 6
Few-shot redirect examples | Medium-High | Low — 2–3 examples in prompt
Application-side tangent detection | High | Low — regex pattern list
Conditional branching in code | Very High | Medium — getNextStep() function
Multi-agent architecture | Very High | High — separate controller + responder agents
Practical recommendation
For most use cases, combine state injection + typed validation + anti-drift prompt + tangent detection. This handles ~90% of drift scenarios without the overhead of a full multi-agent architecture. Add multi-agent only when form logic is highly complex or when errors have significant real-world consequences.
Agent | Responsibility
Controller agent | Owns the state machine. Decides which step is active, validates answers, handles branching. Never exposed to the user directly.
Responder agent | Handles only the current step. Receives a narrow context window with a single question. Generates natural-sounding responses.
FAQ handler (optional) | A third agent that handles tangential questions and returns a flag to bring the user back. Keeps the responder agent focused.
Symptom | Root Cause + Fix
Agent forgets which step it's on | State not injected every turn. Add state to system prompt on each API call.
Agent answers off-topic questions | Missing anti-drift instructions or tangent detection. Add both.
Agent accepts invalid/empty answers | No validation layer. Add validate() to each step.
Agent skips required steps | Conditional logic inside the prompt. Move all branching to getNextStep() in code.
Agent re-asks already-answered questions | Collected answers not included in injected state. Add answers map to prompt.
Agent completes form prematurely | Done condition triggered too early. Add explicit terminal flag and check all steps.
