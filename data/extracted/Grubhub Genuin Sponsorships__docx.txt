Grubhub × Genuin
Offsite Video Sponsored Post and Takeovers
Overview
Part 1 — What We Are Building
Grubhub and Genuin are partnering to power offsite video sponsored posts and takeovers for Grubhub's restaurant network on brand partner destinations — beginning with iHeart. Genuin's platform serves short-form restaurant sponsored posts within iHeart's destination, with Grubhub's data informing which video a given user sees.
Part 2 — How It Works
The integration is entirely offsite and server-to-server. Genuin's SDK runs on iHeart's destination — not inside the Grubhub app. When a user encounters a Genuin video placement on iHeart, the SDK calls Grubhub's backend in real time to determine which restaurant videos to show that specific user. For SMB campaigns, this call includes non-PII location signals that Grubhub uses to match the user to nearby restaurants.
This document covers the five technical components required to make the integration work end to end:
1. Runtime Flow
The integration operates on a fully server-to-server model. Genuin SDK runs within the brand partner's destination (e.g. iHeart), which reaches Grubhub's backend to fetch personalised video recommendations at runtime via Genuin’s backend. The SDK initializes as soon as the destination loads and requests a personalised video feed immediately. Videos begin playing only when the placement scrolls into the user's viewport. Path 1 — BCC Admin Portal
The Genuin admin portal supports manual video uploads (drag-and-drop, up to 2GB) and URL-based imports from YouTube, Vimeo, or any direct video URL. This path is best suited to initial onboarding and one-off uploads.
Path 2 — RSS / MRSS Feed
Genuin pulls from a standard RSS or MRSS feed URL on a configurable schedule. Standard feed fields are used — custom metadata extensions are not yet supported in Phase 1. This is the primary programmatic ingestion path for Phase 1.
Path 3 — JSON Endpoint
Genuin polls a JSON endpoint URL provided by Grubhub on a configurable schedule. The endpoint must return a videos array with standard fields: id, title, video_url, and duration (required); description, thumbnail, and published_at (optional). Field name mapping is supported if the API uses different names. This path is scoped for Phase 2.
3. Video Metadata Retrieval
Grubhub's system retrieves the video catalogue held in Genuin via a paginated REST API, called on a nightly batch cadence.

4. Identity Matching
Because the Genuin SDK runs on a brand partner destination (e.g. iHeart), Grubhub cannot rely on cookies or authenticated sessions to identify the user. Instead, identity resolution uses non-PII signals present in every request. Two resolution options are available.
Figure 4 — Identity Matching: Decision tree showing Option A (native) and Option B (third-party resolution)
Available Signals (Non-PII)
The Genuin SDK collects the following signals from the device environment and passes them to Grubhub's endpoint:
IP address + request timestamp
User agent string
Device type, operating system, and OS version
Browser name and version (mobile web) or app bundle ID (in-app)
Option A — Grubhub Native Match
Grubhub's backend resolves the incoming signals against its own user graph. For logged-in users, this is a deterministic match (email or Grubhub user ID derived from session). For anonymous users, Grubhub applies probabilistic matching based on device fingerprint and IP heuristics. The resolved identity is used internally — it is never returned to Genuin.
Option B — Third-Party Resolution
For scenarios where Grubhub's native match rate is insufficient, a third-party identity graph can be introduced as an intermediary. The graph receives the non-PII signals, resolves them against its cross-device graph, and returns a unified ID that Grubhub can use for recommendation lookup.
5.
The Three-Level Hierarchy
Each level serves a distinct purpose in organising and delivering restaurant video content:
Community — the top-level container, corresponding directly to one restaurant. Each Community is identified by a Genuin UUID and mapped to a Grubhub restaurant name. One restaurant always equals one Community.
Group — a collection of related videos within a Community, organised by theme or category (e.g. "Spring Menu", "Limited Offers"). In Phase 1, each Community has exactly one Group.
Video — the individual sponsored video clip within a Group. In Phase 1, each Group contains exactly one active video.
Phase 1 — One Restaurant · One Community · One Active Video
In Phase 1, the relationship between Grubhub and Genuin is entirely name-based. When Grubhub's recommendation engine resolves a user's location and returns a restaurant name, Genuin performs a direct lookup against its Community index. Each Community has exactly one Group with one video marked as active. The serving logic requires no video identifier, no ranking, and no additional matching step.
Phase 2 — One Community · Multiple Videos
Once the Phase 1 integration is validated, the one-video constraint can be lifted. A single Community (restaurant) can hold multiple Groups, each containing multiple videos. This requires a mechanism for Grubhub to signal which video — or ranked set of videos — should be served for a given user. The specific mechanism (video selection signals, a partner_video_id field, or contextual matching) will be defined during Phase 2 scoping.
